# 运行中一轮的实时推送

## 为什么改

原来的流程是：连接器收到任何事件，攒 200 ms 发“状态有变化”；手机再等 250 ms，发 `session.read`；连接器重读整个会话（连接器自管的会话要调用 `thread/read includeTurns`），逐轮序列化和哈希后回传。每次更新要多走一个来回，文字成块出现。

另外，Codex 0.170 的 `thread/read` 不返回正在输出的回复，持久化后的条目 ID 也和实时事件不同（`item-3` 对 `msg_…`）。所以连接器自管的会话在回复结束前，手机上一个字都看不到。

## 现在怎么做

1. 手机打开会话时，`session.read` 带 `watch: true`，并向中继发 `{type:'watch'}`。连接器把这个会话标记为“正在看”，30 秒内未续期则失效。手机每 10 秒的兜底刷新会续期。
2. 连接器维护运行中的一轮：
   - 连接器自管的会话：由 `turn/started`、`item/started`、`item/completed` 和各类 `…/delta` 通知拼出（`src/connector/live.ts` 的 `RuntimeLive`）。读会话时也会把这一轮叠加进快照，所以快照里同样有正在输出的文字。
   - 跟随桌面的会话：桌面补丁按路径复制合并，未改动的部分保持原对象。补丁只落在当前一轮内、且手机能看到的其他字段没变时，视为“只改了这一轮”。
3. 只改了这一轮时，连接器不再发“状态有变化”，而是每 40 ms 合并发送一帧 `{type:'live'}`：
   - `{i, o, t}`：条目 `i` 在第 `o` 个字符处追加 `t`
   - `{i, item}`：新增或替换条目
   - `fields`：轮次状态、错误、改动等字段
   - `turn`：条目列表结构变了时，整轮发送
4. 其他变化（新一轮开始、审批、排队、结束、旧轮次改动）照旧发“状态有变化”，延迟从 200 ms 降到 60 ms，手机收到后立即取快照（不再等 250 ms）。
5. 手机按动画帧合并应用推送。已有的文字跳过；出现缺口、未知条目或连接代次不同时，重新取快照。快照到达时，如果这一轮还在运行、本地文字比快照更长且以快照内容开头，保留本地文字。

中继只把 `live` 帧转给正在看该会话的手机。中继在 `ready` 里声明 `features: ['live']`；连接器只在新中继下启用推送，连接旧中继时仍用原来的变化通知。手机和中继之间启用 permessage-deflate。

## 其他改动

- 发送即显示：点发送后，消息立即以“正在发送…”出现在会话里，输入框清空。被拒绝时恢复输入并提示原因；结果不明时标记“结果待核实”。会话中出现新的用户消息后，这条临时消息消失。
- 会话缓存：内存保留最近 24 个会话，IndexedDB 保存最近 10 个（每个最近 20 轮，不含图片）以及会话列表。切换或重新打开时先显示缓存，标记为非实时，刷新完成前不能发送。“断开连接”时清除。
- Service worker：缓存页面及其引用的全部版本化文件，打开时不等网络。新版页面在后台下载齐全后才替换。
- 长回复按顶层块分别渲染，流式输出时只重新解析最后一块（`web/markdown-blocks.ts`）。
- 键盘弹出时的视口变量每帧最多写一次，值不变不写。
- 时间线关闭浏览器自带的滚动锚定，统一由应用处理；内容在底部收缩时仍视为跟随到底部。

## 测量

测试环境：本机运行真实的 Codex 0.170 app-server、连接器和中继，手机端为 Playwright 模拟的 iPhone 13。在手机到中继、电脑到中继两段各加 40 ms 单程延迟（相当于 80 ms 往返）。模型由本地夹具代替，回复分 33 段，每段间隔 90 ms；桌面会话由模拟的桌面 IPC 发出 19 个补丁。

| 指标 | 改动前 | 改动后 |
| --- | --- | --- |
| 点发送到自己的消息出现 | 785 ms | 51 ms |
| 连接器会话：首字比模型晚 | 3170 ms（回复结束才出现） | 142 ms |
| 连接器会话：流式期间可见更新次数（共 33 段） | 0 | 32 |
| 桌面会话：首字比桌面晚 | 592 ms | 150 ms |
| 桌面会话：可见更新次数（共 19 个补丁） | 4 | 18 |
| 桌面会话：流式期间整会话重读次数 | 8 | 2 |
| 从列表重新打开会话 | 222 ms | 52 ms |
| 冷启动到显示内容 | 924 ms | 109 ms |
